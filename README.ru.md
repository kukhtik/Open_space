## Swarm — мультиагентная оркестрация с машинной приёмкой

**Проблема.** LLM-агенты отчитываются «готово», когда работа не сделана — молча падают, оставляют заглушки, зацикливаются. Одиночный агент, проверяющий себя сам, страдает подтверждающим искажением.

**Подход.** Изоляция ролей: планировщик декомпозирует задачу в проверяемые шаги, исполнитель делает работу, верификатор открывается с чистым контекстом и судит исполнение — pytest, линтер, dry-run — а не слова агента.

![Swarm — архитектура](screenshots/swarm-architecture.png)

| Механизм | Как устроен |
|---|---|
| **Изоляция ролей** | Планировщик / исполнитель / верификатор — разные личности и контексты |
| **Закрытая петля** | Выход каждого инструмента проверяется детерминированно до следующего шага |
| **Защита границ** | Файлы `scope.protected` прибиты SHA-256; правка = автопровал задачи — ловятся и правки, и удаления (проверено механически) |
| **Бюджет и эскалация** | Ограниченные ходы и попытки; после N провалов — эскалация к сильной модели или человеку по политике из пакета задачи |

Референсный прогон (`demo-calc-bugfix`): оракул `python test_calc.py` → `ALL TESTS PASSED`, 11/11 проверок зелёные, 4 хода, 21 с, tamper false.

![Swarm — живая канбан-доска](screenshots/swarm-kanban.png)

**Открытый код:** [hermes-reform](https://github.com/kukhtik/hermes-reform) — 21 влитая ветка реформы (стабильность ядра, security-база, desktop-стабильность), CI + независимое ревью моделями. Там же runbook сопутствующего мультипрофильного шлюза: один Telegram-бот на 13 профилей агентов через DM-топики (маршрутизация thread → профиль).

**Стек:** Python · Hermes Agent (канбан-диспетчер, middleware) · pytest как оракул · SHA-256 tamper-check · JSONL-траектории.

## GeoConverter — численная калибровка геодезических координат

**Проблема.** Перевод координат между унаследованными локальными системами и современными глобальными датумами (WGS-84) требует субмиллиметровой точности при сильных нелинейных искажениях. (Конкретные системы и зоны — конфиденциальны.)

**Подход.** Четырёхстадийный численный конвейер с обратной проверкой: замкнутый маршрут должен сойтись в пределах миллиметров.

![GeoConverter — главное окно](screenshots/geoconverter.png)

Опорные точки → **Helmert 3D (SVD)** → **Левенберг–Марквардт** → **Нелдер–Мид** (допуск 1e-12) → контроль ошибки замкнутого маршрута.

![GeoConverter — сгенерированный отчёт](screenshots/geoconverter-report.png)

**Коммерческий desktop-продукт** (Windows 7/10): аппаратно-привязанные ключи активации без внешнего сервера, встроенный выпуск лицензий, UI на PyQt6, автоматический разбор смешанных данных из AutoCAD, CSV и Excel.

**Стек:** Python · NumPy / SciPy (least_squares, SVD) · PyQt6 · PyInstaller / Nuitka.

## VETKA_DWG — полевые абрисы → чертежи CAD

**Проблема.** Геодезист рисует полевой абрис (набросок с нумерованными точками) и потом часами переносит его в CAD.

**Подход.** Фото абриса → распознавание маркеров и текста → топографический DXF/DWG. **4 часа ручного черчения → 15 минут.** В продакшене у геодезических компаний (Беларусь).

![VETKA_DWG — аудит библиотеки блоков](screenshots/vetka-dwg-library.png)

На скриншоте — консоль аудита библиотеки блоков: **444 / 444 блока проходят все пять осей точности** относительно эталонного шаблона (библиотека знаков ГУГК, ШАБЛОН‑2025).

**Стек:** Python · собственный CV-пайплайн (детекция маркеров, OCR) · ezdxf · библиотека знаков ГУГК на 444 блока · PySide6 / QML · CI с quality gates.

## VTuber Rigger — авто-риггинг: модель или скриншоты → VRM 1.0

**Проблема.** Риггинг VTuber-аватара — скелет, скин-веса, выражения, spring-bones — занимает часы ручной работы в Blender, а реконструкция из плоского изображения (скриншоты) сложнее вдвойне.

**Подход.** Два пути, полностью локально (без платных API): **Path A** — 3D-модель (GLB/GLTF/VRM/OBJ) → VRM 1.0; **Path B** — скриншоты спереди/сбоку/сзади → VRM 1.0. Сегментация тела на K-Means + кривизне, предиктор 53-костного VRM-скелета, скин-веса RBF + Laplacian, 17 выражений, spring-bones для волос/одежды, QA-гейты headless-VRM и LPIPS/CLIP.

![VTuber Rigger — прогон пайплайна](screenshots/rigger-pipeline.png)

Референсный прогон на тестовой меш-модели: `GLB → VRM`, exit 0, **54 узла, 1 меш, расширения `VRMC_vrm` + `VRMC_springBone`**.

**Стек:** Python · trimesh · pygltflib · numpy / scipy / scikit-learn · OpenCV · pytest (unit + integration + property + perceptual). Публичный: [github.com/kukhtik/RIGGER](https://github.com/kukhtik/RIGGER).

## Neuro Property Trade — детерминированный игровой движок + AI-места

**Проблема.** Коммерческую настольную игру нельзя безопасно модифицировать для игры ИИ (анти-тампер, снятые с продажи версии, нет чистого доступа к состоянию). Чтобы ИИ-место играло честно, сама игра должна быть построена так, чтобы состоянием владел движок — а не ИИ.

**Подход.** Самостоятельная игра на Godot 4 с детерминированным движком правил: seeded RNG течёт через один класс, каждое действие идёт через append-only лог событий (полный replay), а ИИ-места (Neuro / Evil Neuro / человек) отправляют **интенты** — движок их валидирует и исполняет; ИИ не может испортить состояние. Оригинальный сеттинг, без чужих торговых марок.

![Neuro Property Trade — тесты движка и демо доски](screenshots/neuro-engine.png)

Живой прогон: **161 headless-тест зелёный**, затем ASCII-снимок доски (позиции, кэш, клетки по местам).

**Стек:** Godot 4.7 (GDScript) · headless-тестируемое ядро · адаптер Neuro SDK (WS протокол действий, реестр действий, контекст хода). Публичный: [github.com/kukhtik/neuro-property-trade](https://github.com/kukhtik/neuro-property-trade).

## Торговый исследовательский стенд — систематическая валидация стратегий

**Проблема.** Большинство «прибыльных» розничных стратегий умирают после комиссий и слиппеджа; обычный бэктест это как раз и скрывает.

**Подход.** Исследовательский стенд, а не сигнальный бот: walk-forward бэктесты с комиссиями, слиппеджем и фандингом; явные проверки look-ahead bias (сдвиг сигналов на бар); CPCV-консистентность (combinatorial purged CV); риск-контроль (сайзинг, circuit breaker, kill-switch). Paper-режим работает без ключей.

**Измеренный свип** — 33 стратегии на 4 таймфреймах: выше порога PF > 1.1, p < 0.10 и ≥ 30 сделок остаются единицы. Пример на 4h: **PF 1.44, 2 526 сделок, CPCV-консистентность 82%**. Сравнение за тот же год: breakout +6.4% против buy & hold **−52.7%** — активное управление защитило капитал микросчёта.

![Торговый стенд — web UI валидации](screenshots/trading-validation.png)

**Стек:** Python · CCXT · pandas / Parquet · FastAPI + Jinja2 web UI · systemd-юниты. *(Исследовательский стенд — только оценка, не сигналы.)*

## Streaming stateful prediction — исследовательская задача

**Проблема.** Модель должна предсказывать цель по одной строке за раз в потоке: каждая строка зависит от всей предыдущей истории, окно — десятки тысяч строк, а метрика считается блоками внутри последовательности (корреляция, а не MSE). Обычные рецепты (нарезка окнами, MSE-лосс) здесь не работают.

**Подход.** Stateful-рекуррентная модель (GRU, пошаговый экспорт в ONNX) со строгим контрактом состояния: инференс по одной строке, hidden state переносится между вызовами. Ключевое — **метрико-выровненный лосс**: реализация официального блочного агрегата на torch, побитово сверенная со скорером, и корреляция, накапливаемая по всей последовательности (а не по короткому окну, где цель почти постоянна и сигнал тонет в шуме).

Инженерные рычаги, проверенные на практике:

| Рычаг | Результат |
|---|---|
| Метрико-выровненный лосс | одиночная модель обошла лучший ансамбль |
| Горизонт корреляции | на полном окне сигнал в 4–5× сильнее, чем на коротком сегменте |
| Трансформация фич внутри ONNX-графа | наивный пересчёт фич не влезал в лимит инференса; in-graph — влезает с запасом 1.38× |
| Перепроверка документации стакана | заявленная раскладка bid/ask оказалась ложной — найдена перебором пар на 500k строк |

Отдельный пласт — **устойчивость инфраструктуры**: обучение шло на GPU с 4 ГБ в WSL, который молча рестартовал под нагрузкой (утечка page cache через 9p-мост). Решение — `posix_fadvise(DONTNEED)` на каждую группу parquet; кэш стабилизировался.

*Задача соревновательная: подход и инженерные уроки описаны, конкретные данные, метрики и код не публикуются (правила площадки).*

## Neuro Property Trade — детерминированный движок + собственный UI

**Проблема.** Настольную игру нельзя безопасно модифицировать для игры ИИ: анти-тампер, нет чистого доступа к состоянию.

**Подход.** Движок владеет состоянием, ИИ присылает **интенты**: seeded RNG через один класс, каждое действие — в append-only лог событий (полный replay), ИИ не может испортить состояние.
